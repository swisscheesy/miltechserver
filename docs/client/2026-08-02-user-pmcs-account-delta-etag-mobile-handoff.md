## Continuation status

The server-side `changes[].etag` prerequisite is implemented. Every account
delta change now carries the exact opaque strong ETag for the current root
representation returned in that change. This includes:

- active owned checklists;
- owned checklist deletion tombstones;
- active linked subscriptions; and
- subscription unsubscribe tombstones.

The client may use the reviewed server head above to satisfy Step 0 of the
mobile master plan and the ETag gate at the start of Plan 3. Plan 2 wire DTOs
must require and preserve the field before Plan 3 begins.

## What changed on the server

The account-delta change object gained one required property:

```json
{
  "account_change_version": 45,
  "kind": "checklist",
  "etag": "\"opaque-checklist-root-validator\"",
  "checklist": {}
}
```

The ETag is generated by the same server helpers used to validate mutation
`If-Match` headers:

- a checklist change uses the checklist UUID and current checklist
  `sync_version` inside the server's opaque ETag implementation; and
- a subscription change uses the source checklist UUID and current
  subscription `sync_version` inside the server's opaque ETag implementation.

That construction is a server implementation detail. The mobile client must
not reproduce it. If the server changes its ETag algorithm later, an unchanged
client that stores and replays the received string will continue to work.

Account-delta rows already collapse multiple mutations to one root into the
latest complete state. The returned `etag` therefore belongs to that current
complete state, not to a historical change event and not to the page's account
cursor.

## DTO and decoding requirements

Keep `etag` required at the common sync-change level:

```dart
sealed class UserPmcsSyncChangeRM {
  const UserPmcsSyncChangeRM(this.accountChangeVersion, this.etag);

  final int accountChangeVersion;
  final String etag;

  factory UserPmcsSyncChangeRM.fromJson(Map<String, dynamic> json);
}
```

The discriminator accepts only `kind == 'checklist'` or
`kind == 'subscription'`. Treat a missing, non-string, or blank `etag` as a
contract error; do not persist the page or advance its cursor.

JSON escaping and the decoded Dart value are different:

```json
{"etag":"\"opaque-value\""}
```

decodes to the Dart string:

```dart
'"opaque-value"'
```

Those leading and trailing quote characters are part of the HTTP entity tag.
Preserve the decoded string byte-for-byte. Do not strip quotes, add another
pair of quotes, Base64-decode the value, or normalize it.

## Atomic persistence requirements

For each delta page, use one Drift transaction to:

1. verify the response still belongs to the captured Firebase UID;
2. apply every complete checklist or subscription root;
3. store that change's exact `etag` in the root's existing `etag` column;
4. apply deletion/unsubscribe tombstones and embedded installed content;
5. enforce the plan's non-regression rules for `sync_version` and
   `account_change_version`; and
6. persist `through_cursor` only after every root in the page is accepted.

Do not persist `account_version` as the cursor. Do not commit a resource without
its ETag or an ETag without its resource. If parsing, validation, account-scope
checking, or any root write fails, roll back the entire page and retry from the
previous committed cursor.

## Using the stored ETag

Replay the stored string unchanged in the next mutation of the same root:

```dart
final options = Options(
  headers: <String, Object?>{
    'If-Match': storedRootEtag,
  },
);
```

Checklist-root ETags are used for:

- replace draft;
- discard draft;
- publish revision;
- delete owned checklist;
- release a community revision; and
- retire a community source.

Subscription-root ETags are used for:

- accept subscription update;
- unsubscribe; and
- resubscribe from a retained subscription tombstone.

Do not use an installed-release representation ETag for subscription mutation.
Do not use a public-preview or immutable-revision ETag for owned mutation.

Successful mutation responses still return the new root ETag in the HTTP
`ETag` header. Persist that response representation and header atomically. A
later account delta may deliver the same canonical root and ETag to another
device.

## Compatibility and unchanged behavior

This is an additive response-field change. The following did not change:

- route paths, authentication, query parameters, or pagination limits;
- `from_cursor`, `through_cursor`, `account_version`, or `has_more` semantics;
- complete-root collapse and byte-limit behavior;
- owned/subscription JSON resource shapes;
- mutation request or response wrappers;
- HTTP response-header ETags on existing routes;
- PostgreSQL schema, migrations, Jet models, or account-version allocation; or
- the rule that inspections, progress, faults, notes, and history remain local.

Older clients that ignore unknown JSON fields continue to decode the response.
The new mobile sync implementation must not ignore `etag`, because its
cross-device mutation and tombstone workflows depend on it.
