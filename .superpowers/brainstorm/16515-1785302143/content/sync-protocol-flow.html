Synchronization and concurrency flow

Complete aggregates move in version-ordered pages; writes are conditional and account changes cannot commit out of order.

Conditional mutation

1
Read resourceClient receives the complete representation and strong ETag derived from checklist sync_version.
2
Send desired statePUT or DELETE includes If-Match. New client-ID resources use If-None-Match: *.
3
Lock in one orderTransaction locks user sync-state first, then checklist/subscription root, then dependent rows.
4
Validate and commitServer validates ownership, UUID tree, limits, state transition, and publication rules before replacing content.
5
Return canonical stateResponse contains new ETag, server timestamps, normalized models, and the committed representation.

Embedded account delta

1
Request after cursor VServer begins one consistent read snapshot and selects changed roots ordered by account_change_version.
2
Build whole entriesOwned entry embeds current draft + current publication. Subscription entry embeds its installed release. Tombstones contain no content tree.
3
Stop at page boundaryAn aggregate is never split. Entry-count and uncompressed-byte ceilings bound the response.
4
Apply atomically on deviceClient durably applies the complete page before storing the returned through_cursor.
5
Continue if neededhas_more drives the next page. Concurrent later commits have higher versions and appear on a later request.

Delta response contract
from_cursor · through_cursor · account_version · has_more · changes[]
Each change has kind, resource ID, sync version, account change version, ETag, tombstone metadata, and—when active—the complete selected aggregate content.
Concurrent write safety A mutation committed after the delta snapshot receives a later account version. It cannot be hidden behind the page cursor and will be returned on the next pull.
